# Errors and limits

## Compile errors

A front reports every compile error before anything runs, each with its file, line, column and source line. Lox recovers at the next statement and uses the book's messages.

```lox syntax.lox
var x = = 2;
print "one"
```

```text
$ interpreter run syntax.lox
error: Error at '=': Expect expression.
  --> syntax.lox:1:9
  |
1 | var x = = 2;
  |         ^

error: Error at end: Expect ';' after value.
  --> syntax.lox:3:1
```

In Rust, `interpreter::code::compile` returns the diagnostics with the chunk, and `Diagnostic::render_all(&errors, src, Some(path))` writes this report. In a page, `run` resolves with it in `out`.

## Run errors

An error ends the run. Without a `REPORT` of its own, a runtime gets the engine's report with the class, the message, the line and the calls that led there. Lox sets its own, the message then the line, as the book prints it. The CLI writes the report to stderr and exits with 1, shown as `[exit 1]` on these pages. `exit(n)` ends a run with status `n`.

```lox broken.lox
fun half(n) {
    return n / 2;
}

print "before";
print half("ten");
```

```text
$ interpreter run broken.lox
before
Operands must be numbers.
[line 2] in script
[exit 1]
```

| Host | Gets |
|---|---|
| Rust | The `Err(e)` of `vm.run()`. `vm.report_error(&e, src, path)` writes this report, `vm.error_text(&e)` only its class and message, and `vm.system_exit_code()` the status of an `exit` |
| JavaScript | `out` of the value `run` resolves with, and `exitCode` |
| `.wasm` | The `ERROR` or `EXIT` kind of the status word, with the report in the output buffer |

A runtime names every error the engine raises through its `Names` and its `message`, so a runtime of yours decides each class and sentence. See [Build a runtime](./02-runtime.mdx#language).

## Limits

Every run is metered, natives included. A run raises an error at the limit it reaches.

| Limit | Default | Set with |
|---|---|---|
| Operations | 100,000,000 | `Limits { ops, .. }`, `limits.ops` in JS, `--ops`, `set_limits` |
| Memory the run holds | 256 MiB | `Limits { memory, .. }`, `limits.memory` in MB in JS, `--memory`, `set_limits` |
| Call depth | The runtime's `recursion_limit`, 1000 in Lox where it reads as `Stack overflow.` | `Policy` |
| Calls nested through a native or a plugin | 128 | Fixed |
| Comparison depth of nested containers | 100 | Fixed |

`Limits::sandbox()` gives the defaults. Memory is an exact count of every byte the allocator hands the run, so a Rust host installs `interpreter::allocator!()` or sets `memory: usize::MAX`. A spent op budget cannot be caught, since the handler's first op raises again. `reset_budget(ops)` gives a stopped run a new one.

```text
$ interpreter run broken.lox --ops 3
Runtime: budget exceeded
[exit 1]
```

A source has these limits, each reported as a compile error.

| Cap | Value |
|---|---|
| Source size | 10 MiB |
| Block depth | 100 |
| Nesting of expressions, targets and patterns | 200 |
| Instructions, names or constants per function | 65,535 |
| Call arguments | 255 positional and 255 keyword |
| Native imports per module | 256 |
| Imports nested one inside the next | 64 |

The engine has no clock, randomness, threads or system access of its own. The same source and input give the same output on `x86_64`, `aarch64` and `wasm32`, and only the host modules a grant opens can differ.
